# Purpose

This document defines how AI systems should collaborate on Explorer Academy.

It exists to preserve architectural consistency across multiple AI conversations and future contributors.

Repository documentation is always more authoritative than conversation history.

---

# Primary Responsibility

Your first responsibility is **not writing code**.

Your first responsibility is **protecting the architecture**.

---

# Before Doing Anything

Always read, in order:

1. Project Manifest
2. Project Context
3. Design Decision Log
4. Documentation Index
5. Dependency Graph
6. Generation Roadmap

Only then should you begin work.

---

# Core Responsibilities

An AI contributor should:

- understand the existing architecture
- preserve project philosophy
- identify inconsistencies
- propose improvements
- explain trade-offs
- document assumptions
- avoid duplication

---

# What Never To Do

Never:

- silently change architecture
- contradict approved documents
- duplicate information
- invent new terminology
- skip prerequisite documents
- expose curriculum to learners
- optimise implementation over philosophy

---

# Preferred Workflow

```
Read
    ↓
Understand
    ↓
Analyse
    ↓
Identify Risks
    ↓
Recommend
    ↓
Wait for Approval
    ↓
Generate
```

---

# Decision Hierarchy

When documents disagree:

```
Project Manifest
        ↓
Project Context
        ↓
Design Decision Log
        ↓
Vision
        ↓
Educational Documents
        ↓
Architecture
        ↓
Campaigns
        ↓
Implementation
```

Higher-level documents always win.

---

# Architectural Behaviour

When asked to add a feature:

1. Determine whether the feature already exists.
2. Check affected documents.
3. Explain architectural impact.
4. Recommend the best solution.
5. Wait for approval before modifying foundational documents.

---

# Writing Standards

Every new document should include:

- Purpose
- Scope
- Audience
- Dependencies
- Version
- Status
- Owner
- Related Documents
- Future Considerations

---

# Versioning

Use Semantic Versioning.

- Major → architectural change
- Minor → approved enhancement
- Patch → editorial improvement

---

# Documentation Rules

Every new document must:

- be registered in Documentation Index
- follow repository naming conventions
- declare dependencies
- reference related documents
- avoid duplicating existing content

---

# Communication Style

Be:

- clear
- structured
- evidence-based
- concise
- maintainable

Avoid:

- unnecessary verbosity
- hidden assumptions
- speculative architecture
- undocumented decisions

---

# When Unsure

Do not guess.

Instead:

- identify uncertainty
- explain available options
- recommend an approach
- ask for approval

---

# Long-Term Thinking

Always optimise for:

- extensibility
- maintainability
- future campaigns
- future AI collaboration
- independent learners
- low parental effort

Avoid solutions that only work for Campaign 1.

---

# Definition of Success

A successful AI contribution should leave the repository:

- more consistent
- easier to understand
- better documented
- easier to extend
- closer to the North Star

Every contribution should improve the project—not merely complete the requested task.
